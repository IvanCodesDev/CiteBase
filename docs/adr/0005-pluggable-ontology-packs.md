# ADR-0005：本体可插拔（Ontology Pack），内核零领域词

- 状态：Accepted
- 日期：2026-08-21（设计基线）

## 背景

本项目源自数学建模场景（OpenMathModel），但目标是通用知识基座。通用化的常见失败模式有两种：

1. **领域词烧进内核**：内核 schema 里出现 `method / problem / paper` 这类首发领域的词汇，第二个领域接入时开始打补丁，内核逐渐变成「首发领域 + 例外」；
2. **过度抽象**：为了通用把一切抽象成「节点 / 边 / 属性」，结果任何领域用起来都别扭，卡片正文没有结构纪律。

## 决策

内核只认识 `Source / Card / Claim / Link` 四个抽象 + 内置 `contradiction` 卡类；**领域语义全部由 Ontology Pack 声明**：

- Pack = YAML + JSON Schema 片段：声明 `card_kinds`（含每类的正文分节）、`link_predicates`、`tag_vocab`；
- 内置发行三包：`pack-generic`（概念/方法/陷阱）、`pack-code`（服务/接口/决策/事故）、`pack-research`（论文/数据集/论断）；
- Pack 不含可执行代码（供应链安全，见[威胁模型 §4](../security/threat-model.md)）；第三方可自由发布；
- **机器强制**：内核代码与内置 schema 出现任何领域词汇即 lint 失败（L-CORE-1）——通用性不靠自觉靠规则。

## 后果

**正面**：

- 通用与垂直解耦：垂直需求（含未来 OMM 的 `pack-mathmodel`）全部进 Pack，内核表面积恒定；
- 卡片正文仍有结构纪律（分节由 Pack 定义），不掉进「一切皆节点」的泥潭；
- Pack 是纯声明文件：可评审、可版本化、可组合（一个 vault 可启用多个 Pack）。

**代价（诚实声明）**：

- 多一层间接：新用户要理解「内核抽象 + Pack 词表」两层——用内置三包默认启用来缓解（开箱即用，不感知 Pack 概念也能工作）；
- Pack 演进的兼容性成本：kind 或谓词改名会破坏存量卡——Pack 版本化 + 迁移脚本约定（与 schema 同规则）。

## 被否决的替代方案

1. **领域词进内核，按需扩展**：见背景失败模式一；R4 风险的接受声明写明「内核膨胀即失败」；
2. **完全无 kind 的自由标签**：失去正文分节纪律与受控谓词的前提，检索与治理都退化；
3. **Pack 含插件代码**（自定义校验器等）：表面更强大，实际打开供应链攻击面与执行环境依赖；校验扩展的正确位置是内核规则的配置化，不是任意代码。
